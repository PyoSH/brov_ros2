2026-09-02~03 수조 두 세션의 **질문별** 정리다. 실험 번호가 아니라 **알고 싶었던 것**을
축으로 쓴다. 세션별 절차·원본 수치는 [session_20260903_summary.md](session_20260903_summary.md),
[deadtime_result_to_training.md](deadtime_result_to_training.md),

이 문서를 쓰게 한 우려이고, 결론을 읽기 전에 그 절을 먼저 봐도 된다.

## 0. 출발점

IsaacLab 에서 논문대로 학습한 정책이 Gazebo SITL 에서는 되는데 **실기에서는 3 축이
떨었다.** 정책 성능이 아니라 **"왜 떠는가"** 가 질문이었다. 후보는 넷이었다: 지연,
plant 불일치, 관측 경로, 액추에이터 비선형(deadband). 두 세션은 이 넷을 하나씩
배제하거나 확정하는 순서로 갔다.

## 1. 실기에서 정책은 왜 떠는가

**알려 한 것.** 2 Hz 3 축 진동의 기전. 이득 문제인지, 지연 문제인지, 기체 문제인지.

**실험.**
- A2-heave / A2-yaw: 정책을 빼고 알려진 신호(사각파)를 넣어 명령→가속도 교차상관.
  yaw 는 bias 로 추진기 역전을 없애고 자이로로 직접 잰다.
- A1: 정책 이득 1.0 vs 0.5. 사라지면 "지연+세기", 남으면 다른 것.
- 개루프 bag 의 2 Hz 대역: 기체 자체 공진 유무.
- 행동 포화 비율, 추진기 클램프, 적분기 클램프, deadband 동작점.

**결과.**
- τ = 80 ms (yaw, r 0.81). 위상 예산의 −180° 교차 2.39 Hz ≈ 실측 2.0~2.3 Hz.
- 이득 ½ 에서 진동이 **안 사라지고 진폭만 ×0.4~0.8, 주파수 그대로.**
- 정책이 surge 73 %, sway 67 % 시간 **클램프에 붙어** 있었다. 추진기 T1/T2 도 46~51 %.
- 개루프 bag 에는 2 Hz 가 없다. 적분기 클램프 0 %. deadband 동작점 밖(6 N/추진기).

**해낸 것.** 기전이 확정됐다: **80 ms 지연 아래서 포화(relay)된 정책이 만드는 limit
cycle.** 주파수는 지연이 정하고 진폭은 포화 수준(=이득)이 정한다 — 이득을 낮춰도
꺼지지 않는 이유가 그것이다. plant·공진·적분기·deadband 는 배제됐다.

**부족한 것.** 정책의 순항점 이득 4.5 는 어제 문서 값이고, 정지점에서 재면 1.2~1.9 다.
**이득이 동작점에 따라 3 배 변한다**는 것만 알았지 실제 순항 중의 값은 A1 bag 으로
회귀해 잰 적이 없다. 문턱 3.52 대비 "얼마나" 넘는지는 아직 추정이다.

**해야 하는 것.** 실기 bag 의 `/brov/observation`↔`/brov/cmd/wrench` 로 순항점 Jacobian
(Δwrench/Δv_e)을 잰다. 학습 PC 에서 bag 만으로 된다.

## 2. 지연은 얼마이고 어디서 생기는가

**알려 한 것.** τ 의 크기와 **구간별 몫** — 대응 수단이 구간마다 다르다(테더→온보드
이전, 액추에이터→RC_SPEED, FC 내부→telemetry·라우터).

**실험.** M1 ping, M2 TIMESYNC 왕복, M3 명령→서보출력(도착 시계), M4 서보→자이로
(**FC 시계**, 링크 무관), chirp 0.5→8 Hz 로 τ 정밀화.

**결과.**

| 구간 | 값 | 비중 |
|---|---|---|
| 테더+RPi (M1) | 5.7 ms | 7 % |
| 라우터+FC 수신 (M2−M1) | 15.0 ms | 18 % |
| **FC 내부 + telemetry 생성 (M3−M2)** | **64.4 ms** | **75 %** |
| 액추에이터+자이로 (M4) | ~0 (< 20 ms 분해능) | ~0 % |
| **τ_total (chirp 보정)** | **85.3 ms** | — |

M3 + M4 = 85 = τ_total. chirp 에서 **lag 0 의 상관이 −0.205** — 지연이 없으면 나올 수
없는 값. 링크 jitter 폭 19.7 ms (p10→p90).

**해낸 것.** 예산이 소수점까지 닫혔고, **ESC·추진기·테더는 원인이 아니다**가 확정됐다.
`RC_SPEED` 벤치 시험과 온보드 이전을 **하지 않아도 된다**는 것을 안 것이 이 절의
가장 큰 수확이다 — 둘 다 위험하거나 큰 작업이었다.

**부족한 것.** **64 ms 가 정확히 무엇인지는 모른다.** "FC 내부 + telemetry" 는 M3 에서
M2 를 뺀 잔차에 붙인 이름이지 측정이 아니다. 그 안에 (a) FC 가 RC override 를 받아
서보에 적용하는 시간, (b) SERVO_OUTPUT_RAW/ATTITUDE 생성 주기의 양자화(25 Hz →
평균 ~20 ms), (c) 라우터의 스트림 큐잉, (d) **우리 wrapper 의 송·수신 구조가 더한 몫**
(§6)이 섞여 있다. (d) 를 빼고 (a)~(c) 를 논하면 틀린다.

**해야 하는 것.** §6 의 감사 항목을 먼저 풀고, 그 뒤 telemetry 50 Hz·라우터 교체 A/B 로
(b)(c) 를 가른다. 학습 주입값은 **85 ms 중심 / 40~120 ms 분포**로 갱신했고, 위가
줄면 그때 다시 갱신한다.

## 3. 지연을 학습에 넣으면 해결되는가

**알려 한 것.** 행동 지연 DR(40~80 ms) + 관측 신선도 15 % 로 재학습한 `delayA` 가
실기에서 relay limit cycle 을 없애는가.

**실험.** 같은 프로토콜로 `fixplant`(기존) vs `delayA`, 각 60 s, 같은 자리, 55 s 창 비교.
이어서 `heading_mode:=straight`(180° 선회 제거)로 delayA 재현.

**결과.**

| | fixplant | delayA (align) | **delayA (straight)** |
|---|---|---|---|
| 행동 포화 surge / sway | 58 / 67 % | 7 / 4 % | **4 / 3 %** |
| 행동 포화 yaw | 24 % | 18 % | **0 %** |
| 추진기 클램프 최대 | 46 % | 10 % | **0 %** (T4 3) |
| v_e RMS (s/sw/h) | .191/.167/.079 | .153/.097/.060 | **.111/.045/.028** |
| \|ω\| RMS (r/p/y) | .76/.79/.72 | .50/.40/1.04 | **.15/.16/.11** |
| 2 Hz surge 명령 | 15.6 N | 6.7 N | **6.7 N** |
| 2 Hz sway 명령 | 17.4 N | 10.8 N | **2.7 N** |
| 2 Hz roll 명령 | 11.0 N·m | 4.0 | **0.5** |
| EKF 발산 | 없음(60 s) | **78 s** | **없음 (84 s)** |

**해낸 것.** 셋이다. (1) 지연 DR 이 **포화를 없앴다**(58→7 %) — 이득만 낮춘 A1 은
못 했던 것이라, 근본 대응이 학습 쪽이 맞았다는 증거. (2) sway·roll·yaw 의 2 Hz 는
지연 DR 의 한계가 아니라 **미션 기하(반복 180° 선회)가 만든 것**이었고, 선회를 빼자
×0.13~0.25 로 무너졌다. (3) EKF 발산도 **회전이 원인**이었고 회전을 빼자 사라졌다.

**부족한 것.** **surge 축 2 Hz 6.7 N 은 heading_mode 와 무관하게 그대로다.** 이것이
dead-time limit cycle 의 진짜 잔여이고, delayA 도 straight 도 건드리지 못했다.
수용 기준 중 "surge ≥ 0.2 m/s" 는 0.17 로 미달. 그리고 위 표의 v_e·속도는 EKF 속도
기반이라, 위치가 수조를 벗어난 구간에서는 신뢰가 조건부다(명령·자이로 지표는 무관).

**해야 하는 것.** surge 2 Hz 를 잡는 두 길 — τ 를 줄이거나(§2), 지연 DR 을 더 넓히거나
(상한 120 ms, 관측 지연 jitter 포함). 후자는 학습 PC 에서 SITL + 80 ms 인공 지연으로
먼저 가른다.

## 4. 센서·추정 경로를 믿을 수 있는가

**알려 한 것.** EKF 수직 위치(SITL 에서 얼어붙었던 것), DVL 의 상태, 관측의 신선도.

**실험.** 깊이 게이트(압력을 자로 EKF z 회귀), `attitude_age_s` 분포, 속도 정보 갱신률,
EKF flags, A50 REST 폴링(TCP 슬롯 안 씀).

**결과.**
- EKF z 는 Bar30 을 따라온다(기울기 1.005, R² 0.9935). **SITL 증상 없음.**
- 관측 신선도: 75 % 가 10 ms 미만, **15 % 가 40~50 ms** — 6 번에 1 번 한 틱 묵음.
- DVL: 정지 시 beam3 상시 무효(3/4), **주행 중 `velocity_valid` 61 %**, 빔별 무효 31~36 %.
- `dvl_record_node` 를 켜면 A50 TCP 슬롯을 뺏어 BlueOS extension 이 죽고 EKF 가
  위치를 잃는다 — 노드를 내려도 회복 안 됨, 재부팅으로 복구.

**해낸 것.** `depth_source:=mavlink_ekf` 유지에 근거가 생겼다. DVL 기록 노드의 위험이
사실로 확인돼 기본 off 로 바꿨고, TCP 슬롯을 안 쓰는 REST 폴링 경로를 찾았다.
"`ekf_velocity_variance`=0 은 융합 없음" 이라는 어제 해석은 **틀렸음**을 flags 로 확인.

**부족한 것.** **A50 이 한계 상태로 돈다.** 회전을 줄여 EKF 가 버틴 것이지 DVL 이
나아진 게 아니다. `/brov/state.valid` 는 발산 중에도 true 였다 — 이 게이트는
추정 발산을 잡지 못한다. EKF flags 를 bag 에 남기지 않아 발산 순간에 EKF 가 무엇을
잃었는지 사후에 볼 수 없었다.

**해야 하는 것.** (1) A50 점검 — beam3 물리 상태, 장착 높이(altitude 0.46~0.66 m 는
A50 최소 0.05 m 위지만 빔이 흔들림). (2) `BrovState` 에 `ekf_flags` 추가(메시지 변경,
전체 재빌드). (3) `state.valid` 에 EKF `POS_HORIZ_REL` 비트를 조건으로 넣을지 검토.

**해낸 것**

## 6. 구현이 병목을 고착시켰을 가능성 — 감사

**우려.** ROS wrapper 를 만들며 "우선 되는 것" 을 먼저 통과시키느라, telemetry 와
제어 명령의 **입력 경로·주기가 검증 없이 굳었을** 수 있다. §2 의 "FC 내부 64 ms" 가
사실은 wrapper 가 더한 몫을 포함하는지가 핵심이다. 이것은 정당한 우려이고, 아래는
코드를 다시 읽어 **무엇이 검증됐고 무엇이 가정인지**를 나눈 것이다.

### 6-2b. G1·G2 — SITL 선행 검증으로 닫힘 (2026-09-03, 학습 PC)

**G1 판정: 배선은 유죄, FC는 무죄, 그리고 cap 의 정체는 G2 였다.**

1. `telemetry_rate_hz` 를 base_node 파라미터로 노출 (split_stack·deadtime_test
   launch 인자 포함, 기본 25 = 기존 동작, 범위 가드 1~100).
2. **FC 는 요청을 지킨다** — wrapper 없이 bare pymavlink 로 같은 직결 경로에
   요청하니 50/100 Hz 를 정확히 송출 (SCHED_LOOP_RATE 400). ACK 는 wrapper
   경유와 동일(result=0)이었다.
3. 그런데 토픽은 25 Hz 그대로였다 — 원인은 **G2 틱 샘플링**: 원시 센서 토픽이
   25 Hz 제어 틱에서 발행돼 도착 표본의 절반을 버렸다. **토픽 주기는 도착률의
   증거가 아니었다** (실기 세션의 "속도 정보 21.5 Hz" 관측도 같은 왜곡).
4. **제어 경로는 이미 이득을 받고 있었다** — 틱이 최신 스냅샷을 쓰므로.
   실측: τ(명령→state 응답, open-loop yaw, 부그리드) **30.6 → 19.1 ms
   (−11.5 ms)** — "양자화 평균 20→10 ms" 예측 적중.
5. **G2 최소 수정 적용**: 원시 센서 토픽을 전용 100 Hz 타이머로 이관(seq 가드
   유지). 결과 ahrs 50.0 Hz / servo 48 Hz 로 도착률이 그대로 보인다.
   `/brov/state` 는 25 Hz 유지 — 정책 계약 불변. M3/M4 의 FC-stamp 분해능도
   이만큼 좋아진다. 완전 이벤트 구동(원판 G2, 반나절)은 100 Hz 폴링 오차
   ≤10 ms 라 당분간 불필요.

**실기에 남은 것**: `telemetry_rate_hz:=50` 으로 A2 재측정 한 번 — 예상 τ
85.3 → ~75 ms. FC CPU 여유(실 Pixhawk)만 실기에서 확인.

### 6-2c. G3 — SITL A/B 로 닫힘 (2026-09-03, 학습 PC)

`actuation_backend` 실험 스위치(rc_override | do_set_servo, 진단 전용)를 배선해
직결·telemetry 50 Hz 동일 조건에서 A2-yaw A/B:

| | rc_override | do_set_servo |
|---|---|---|
| M3 (명령→서보출력) | 30.0 ms | **30.0 ms** |
| \|r\| | 0.998 | 0.998 |

**판정: 차이 없음.** RC override 를 FC 가 "조종사 입력"으로 해석하는 경로는
DO_SET_SERVO 대비 추가 지연이 없다 — 같은 펌웨어 로직이므로 실기에도 구조가
같다(절대값은 실기 FC 에서 다를 수 있으나 경로 간 차는 구조의 문제다).
"M3−M2 = 64 ms 를 override 경로 탓으로 돌렸을 가능성"(6-2 G3)은 **기각** —
잔차의 초점은 G4(라우터/전용 endpoint)와 telemetry 생성으로 좁혀진다.
부수: DO_SET_SERVO 는 8ch×25 Hz COMMAND_LONG + ACK 홍수에서도 SITL 이 견뎠다
— 그래도 진단 전용이며 미션 사용 금지(§6-2 G3 표의 우려는 rate 가 아니라
경로였고, 그 답이 "차이 없음"이다).

부수 실측 (같은 A/B 에서): telemetry 50 Hz 가 M3 자체를 45 → **30 ms** 로
줄였다(서보 스트림 양자화 20→10 ms). G1 의 이득이 M3 에도 그대로 보인다.
SITL 직결의 링크가 ~0 이므로 SITL "FC 내부" 몫은 ~20 ms — 실기 64 ms 와의
차 ~44 ms 가 실기에서 라우터+RPi+실 FC 쪽에 있다는 뜻이다.

### 6-3. 판단

- **G1 은 확실한 고착이다.** 25 Hz 는 정책 dt 에서 온 값을 telemetry 에도 그대로 쓴 것이고,
  telemetry 는 정책보다 빨라도 된다(관측 노드가 최신을 쓰면 됨). 계획서 §6b 가 "보조
  수단" 으로 적어 두고 시험하지 않았다. **다음 실기의 첫 항목이어야 한다.**
- **G2 는 G1 과 짝이다.** 50 Hz 로 올려도 타이머 샘플링이면 이득이 절반만 난다.
  이벤트 구동으로 바꾸면 양자화 자체가 사라진다. 다만 관측 노드→정책의 25 Hz 계약은
  유지해야 하므로, base_node 만 이벤트 구동으로 하고 관측은 최신값을 25 Hz 로 뽑는
  구조가 된다.
- **G3 이 64 ms 의 가장 큰 미지수다.** RC override 는 "조종기 입력" 경로라, ArduPilot 이
  그것을 읽는 주기와 내부 필터가 서보 출력까지의 지연을 더할 수 있다. 우리는 이
  경로를 **한 번도 다른 경로와 비교하지 않았다.** M3−M2 = 64 ms 를 "FC 내부" 라
  부른 것은 이 경로의 비용을 FC 탓으로 돌린 것일 수 있다.
- G4·G6·G7 은 작을 것으로 보지만 **그 "작을 것" 이 가정**이다. 셋 다 한 시간 안에
  숫자로 바뀐다.
- G5 만 wrapper 의 고착이 아니다.

**정직한 요약.** §2 의 "FC 내부 64 ms" 는 **wrapper 의 G1+G2+G3 몫을 포함한 잔차**다.
셋을 풀기 전에는 64 ms 중 얼마가 FC 이고 얼마가 우리 것인지 말할 수 없다. 이 우려는
맞고, 다음 실기의 우선순위는 §5 표의 1 번(=이 절)이 돼야 한다.
